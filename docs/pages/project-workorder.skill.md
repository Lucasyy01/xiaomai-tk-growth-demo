# Page Skill - Project Workorder

## 页面定位
这个页面不是项目列表页，也不是多项目总览页，而是“单项目工单详情页”。

它承接的是一个已经完成客户准入、完成启动准备、正式进入执行阶段的具体项目，用来帮助业务统一查看这个项目当前的执行状态、关键阻塞、责任归属和下一步动作。

## 主要用户
第一用户：
- 项目经理
- 交付负责人
- 运营 / 执行同学

第二用户：
- 客户成功
- 管理者
- 财务协同角色

## 页面主问题
用户进入页面后，最想快速知道：
1. 当前这个项目处于什么状态
2. 当前项目最大的阻塞或风险是什么
3. 当前有哪些关键任务在推进，谁在负责
4. 内容供给与测试准备是否形成闭环
5. 当前项目是否受到授信、预算、回款等约束影响
6. 下一步最值得推动的动作是什么

## 页面成功标准
看完页面后，用户应该能完成以下判断：
- 判断项目当前是正常推进还是存在阻塞
- 判断当前最需要处理的风险是什么
- 判断谁在负责推进当前关键任务
- 判断内容 / 素材 / 测试是否具备继续推进条件
- 判断当前项目下一步应该优先推动什么

## 信息优先级

### 第一优先级
- 当前项目身份（项目名、客户名、项目类型）
- 当前状态
- 当前阻塞 / 风险
- 当前负责人
- 当前唯一主动作

### 第二优先级
- 当前关键任务推进情况
- 内容 / 达人 / 素材 / 测试状态
- 当前是否存在预算 / 授信 / 回款约束

### 第三优先级
- 补充说明
- 弱提醒
- 次级历史信息

## 页面结构建议

### A. 页面头部
展示：
- 页面名称：项目工单详情
- 项目名称
- 所属客户
- 当前状态标签
- 当前负责人
- 返回上一级入口
- 页面级唯一主动作

### B. 项目总览区
优先回答：
- 当前项目处于哪个执行阶段
- 当前是否存在阻塞
- 当前任务完成度如何
- 当前测试 / 执行状态如何

这里要做“管理摘要”，不是纯数字统计看板。

### C. 执行推进区
这是本页核心区块。

建议重点表达：
- 当前关键任务
- 当前状态
- 是否阻塞
- 负责人
- 下一步动作

目标是让用户快速知道：现在谁在推进什么。

### D. 内容与测试区
重点回答：
- 达人合作是否推进
- 素材是否产出 / 授权
- 小预算测试是否开始
- 当前是否具备继续推进条件

这块要服务“内容供给到测试推进是否形成闭环”的判断。

### E. 风险与约束区
重点回答：
- 当前主要阻塞原因
- 授信摘要
- 预算 / 占额 / 回款约束
- 是否影响项目继续执行

这块不是完整财务页，而是“项目推进视角下的约束摘要”。

## 动作系统
本页应坚持“一页一个主动作”。

主动作必须与当前项目状态绑定，例如：
- 推进授权并开始小预算测试
- 处理当前阻塞项
- 催收达人素材交付
- 确认测试结果并进入放量判断

不要在多个区块重复放置同等级 CTA。
不要把页面做成到处都是按钮的操作页。

## 页面不应该变成什么
不要把这个页面做成：
- 多项目总览页
- 纯任务管理工具
- 纯 BI 大屏
- 纯资料展示页
- 所有模块都展开的大杂烩工作台

## 第一轮 UI 改造目标
第一轮不深改业务逻辑，先做到：
- 页面更像成熟 SaaS 的单项目执行明细页
- 当前状态、关键阻塞和下一步动作更清楚
- 执行推进区真正成为页面核心
- 内容与测试区能体现业务闭环
- 风险与约束区足够表达当前限制
- 页面避免大而全，先覆盖最关键流程
